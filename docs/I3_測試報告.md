# I3 多 Agent 協作（LangGraph）：測試報告

- 日期：2026-11-04
- 截圖：`docs/過程截圖/I3_多Agent/`；評測報告：`docs/評測/AI評測報告_20261104_*.md`

## 1. 做了什麼
AI 客服多一個「多 Agent 協作」模式（畫面上可切換，原本的單一 Agent 保留）：

```text
客人訊息 → 分流（拆題）─┬→ 報價專員（只拿報價那段，只有報價工具）─┐
                         ├→ 規定專員（只拿規定那段，只有規定工具）─┼→ 檢查員 ─通過→ 組合回覆
                         └→ 接待專員（打招呼、無關問題、客訴）────┘    └不通過→ 退回原專員重答（最多 1 次）
```

| 角色 | 做什麼 | 用 AI 嗎 |
|---|---|---|
| 分流 | 判斷交給誰，同時問報價和規定就拆成兩個問題（強制用 route 工具輸出，格式固定） | 是（Haiku） |
| 報價／規定／接待專員 | 各自只拿到自己的問題與工具（權限最小）；兩位以上時平行執行 | 是（Haiku） |
| 檢查員 | 程式檢查：金額要出現在工具結果或客人原話；規定要附條號；不能用性別稱謂；說轉專人就要真的建立轉接單 | 否（不花錢） |
| 組合回覆 | 依固定順序合併各專員的回答 | 否 |

- 框架：LangGraph（StateGraph、條件分支、平行、退回重答的迴圈）；每個節點仍用官方 Anthropic SDK，沿用原本的 `run_loop` 與工具。
- 金額改了一次還是對不上：不把可能錯的金額給客人，改成建立轉接單。
- 紀錄：每次經過哪些 Agent（`ai_turns.agent_path`）、每個工具是哪位專員呼叫（`ai_tool_calls.agent`），後台「AI 對話紀錄」看得到。
- AI 評測可以選「評測多 Agent 版」，同樣 20 題。

## 3. 單一 Agent 和多 Agent 怎麼選（面試常問）
| | 單一 Agent | 多 Agent |
|---|---|---|
| 分數 | 20/20 | 20/20 |
| 花費（20 題） | US$ 0.0114 | US$ 0.0151（多一次分流呼叫） |
| 優點 | 簡單、便宜、上下文完整 | 權限分離、每位專員規則短好維護、有獨立檢查員、可平行、可追蹤每一步 |
| 缺點 | 規則和工具越加越多會越難管 | 多一手就可能失真（I3-4）、專員彼此看不到結果（規定專員不知道報價總價，無法直接算退費金額） |

結論：目前規模單一 Agent 就夠用；多 Agent 的價值在「規則變多、要分權限、要有獨立檢查」的時候。系統兩種都保留，用評測決定。

## 4. 遇到的問題（詳見錯誤紀錄 I3-1～I3-4）
1. 檢查員把客人自己說的預算當成亂編的金額（太嚴格的誤判）。
2. 專員把不屬於自己的部分推給對方。
3. AI 說「已轉專人」但沒有真的轉。
4. 分流拆題時把「0 個人」改成「一個人」。

每個問題都補了模擬測試，避免再犯。

## 5. 未測項目
- 多輪長對話（超過 3 輪）的穩定度只有評測 Q20 一題。
- 尖峰時的延遲：多 Agent 要多一次分流呼叫，平行專員可抵消一部分，未做壓力測試。
